# G.722.1 / SVAC 可行性评估

> 结论先行：**G.722.1 解码可以直接做（无授权障碍）；G.722.1 编码需要你先向 Polycom 拿到
> 免费授权；SVAC 没有开源实现，必须买厂商 SDK。** 这三件事的代价差一个数量级，别混在一起排期。

## 1. 现状（2026-11-04 实测）

| 项 | 事实 |
|---|---|
| ffmpeg 里的 G.722 | `g722` 是 G.722 **ADPCM（64kbps）**，和 G.722.1 **不是同一个东西** |
| ffmpeg 里的 G.722.1 | 有：`siren` 解码器（`D.AIL. siren`）——**只有解码，没有编码** |
| ZLM fork 的 codec 枚举 | 有 `CodecG722`(18)、`CodecG723`(19)、`CodecSVACV`(16)、`CodecSVACA`(17)；**没有 G.722.1** |
| 盒子上有没有 g722_1 库 | 没有（`/usr/lib64`、rpm 包都没有） |
| SVAC | ffmpeg 完全不支持；ZLM 只有枚举，没有编解码实现 |

## 2. G.722.1 的授权事实

- G.722.1（Siren7）/ G.722.1 Annex C（Siren14）**使用了 Polycom 的专利**。
- Polycom 提供**免费（royalty-free）授权**，但需要按他们的规则**主动申请**，不是自动生效。
- 开源实现 `freeswitch/libg7221` 摘自 Polycom 参考代码，Polycom 同意以源码分发。
  其 README 明确提醒：**放进 GPL 项目可能有问题**（除非把编解码器作为独立进程，用管道/socket 通信）。
  ZLMediaKit 是 MIT，不冲突，但**商用前仍应把授权函办下来**。

## 3. 三条路与代价

### A. G.722.1 解码（作为转码源）—— 可以立刻做

用它把「G.722.1 进来的流」转成 AAC/Opus/H.265 组合。工作量：

1. `src/Extension/Frame.h` 增加 `CodecG722_1`（需要一个新的 codec 序号，注意与上游冲突风险）
2. 新增 Track 类（RTP 载荷 320 字节/帧、时钟 16000、rtpmap `G7221/16000`）
3. 解码走 ffmpeg `siren`，并在 Transcode.cpp 的解码器选择表里加映射
4. SDP / 转封装支持

**预计 1~2 天**（含真机验证）。没有授权障碍（复用 ffmpeg 的解码器，和我们现在用 AAC/Opus 一样）。

### B. G.722.1 编码（作为转码目标）—— 需要你先办授权

ffmpeg 没有编码器，必须引 `libg7221`（或自写）。两种集成方式：

| 方式 | 优点 | 缺点 |
|---|---|---|
| 静态链进 MediaServer | 延迟低、部署简单 | 专利代码进主二进制，授权边界要写清楚 |
| **独立进程 + 管道/socket** | 授权边界清晰（README 建议的方式）、崩溃隔离 | 多一次 IPC，部署多一个进程 |

**预计 3~5 天**（含 IPC 封装、RTP 打包、真机验证）。前置条件：
**你要先向 Polycom 申请 G.722.1 的 royalty-free 授权**（这是商务动作，我做不了）。

### C. SVAC 音频/视频 —— 不建议自研

SVAC 是国标（GB/T 25724），**没有任何可用开源实现**。要支持只能：

- 向厂商（中星微等）购买 SDK / 授权；
- 或者接受「不支持」，在规格书里写明。

自研 SVAC 编解码器不是人月级的事，不应该进入转码模块的排期。

## 4. 建议

1. **先确认业务是否真的需要**：G.722.1 是 VoIP/会议场景的音频；SVAC 是安防监控国标。
   如果客户是港口无人机巡检，两者都大概率不需要 —— 先跟甲方核对规格书，别为了「对齐 Pro 功能清单」白做。
2. 若确实需要 G.722.1：**先办授权，再排 3~5 天做编码**；解码那 1~2 天随时可插入。
3. SVAC 一律走「外购 SDK 或写明不支持」。
