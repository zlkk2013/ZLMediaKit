# 长跑稳定性（soak）

## 为什么单独做

13 套功能验收每套 1~10 分钟，抓不到「缓慢上涨」类问题：引用环泄漏（本项目真实出现过，
muxer 与转码节点互持导致媒体源永不释放）、句柄不释放、线程堆积、内存缓慢爬升，
都只在长时间运行后才暴露。短测全绿不代表可以上现场。

## 判据（五条，缺一不可）

| # | 判据 | 为什么这样定 |
|---|---|---|
| 1 | 每轮 `getServerConfig` < 3 秒返回，且全程存活 | **自死锁不崩溃、只失去响应**：`ps` 绿、端口在听，只有响应时间能证明它还活着 |
| 2 | 预热后 RSS 涨幅 < 15% | 首轮有 JIT/缓存增长，取 20% 时间点做基线再比，避免误判 |
| 3 | 文件描述符增长 < 50 | 连接泄漏最直观的口径 |
| 4 | 线程数增长 <= 4 | 线程池按需扩张是正常的，持续快速增长才是问题 |
| 5 | 停掉所有推流端 + 等过 15s 宽限期后，`getMediaList` 里本轮流必须全部消失 | 引用环的直接判据（a6 那次就是靠这条抓到的） |

## 负载形状

两路 1280x720@30 同时转 H265：一路软编（真实 CPU 压力）、一路硬编（覆盖 GPU 路径）。
每轮挂两个观众看 6 秒再断开 —— 覆盖 reader 增删与编码并发，单客户端长连接反而抓不到竞态。

## 用法

```bash
env -u PYTHONPATH python3 scripts/soak_test.py        # 默认 12 分钟
env -u PYTHONPATH python3 scripts/soak_test.py 30     # 30 分钟
```

## 已跑结果

- 4 分钟冒烟：RSS 148160→149984 KB（+1.2%）、fd 120→120、thread 29→29、
  最慢响应 4ms、源全部释放 —— **7/7 通过**
- 更长时长按需跑（建议交付前跑一次 ≥30 分钟）
