# 多卡负载均衡（第 10 项）

## 做了什么

- 配置 `hw_devices="0,1"` 声明可用设备；`hw_device=N` 指定某一路用哪张卡（`-1` = 自动）。
- API 同名参数：`hw_devices` / `hw_device`。
- 自动分配策略：**挑当前在跑路数最少的卡**；同负载取序号小的（结果可预测）。
- 同一个流重推时沿用已绑定的卡，不会在两卡之间来回跳。
- 状态接口 `getTranscode` 的 `tracks[].hw_device` 报出实际分配到的设备号。

分配依据是「正在转码的流数量」而不是 GPU 利用率 —— 读利用率要厂商 SDK（NVML 等），
而同样规格的流每路负载接近，路数已经足够近似均衡。

## 平台差异（必须知道）

| 平台 | 能否按序号选卡 | 说明 |
|---|---|---|
| Windows / Linux + NVIDIA | **能** | 通过 NVENC 的 `gpu` 选项（`av_opt_set(priv_data, "gpu", N)`） |
| Linux + VAAPI | 否 | VAAPI 按 render node（`/dev/dri/renderD128`）区分，不是序号；未接入 |
| macOS + VideoToolbox | 否 | 没有设备索引概念 |

**不支持选卡的平台上，配置不会报错，但会被如实忽略**：打一条 WarnL 说明原因，
状态里 `hw_device` 报 `-1`。绝不假装分到了卡 —— 出问题时这种假绿最难查。

## 验收

`scripts/multi_gpu_test.py` 按平台跑不同覆盖面：

- **无选卡能力的平台（本机 macOS）**：参数面（接受/回显/非法值 -300）+ 诚实性
  （状态报 -1、日志有明确警告）→ **10/10 通过**
- **有选卡能力的平台（Linux/Windows + NVENC）**：额外验 3 路流按负载分到 `0/1/0`，
  关流后计数回落。这段在本机 **SKIP**，尚未在 NVIDIA 机器上跑过。

## 顺带修掉的 API 缺陷

`addTranscode` 以前只要请求里带 `reset=1` 就直接返回 —— 同一请求里的其它参数
被**静默丢弃**，调用方以为下发成功了。现在改成：

- 只带 `reset=1`：维持原语义（清掉覆盖、回落到 ini）
- `reset=1` + 参数：先清空、再按参数重新下发

`multi_gpu_test` 里有一条专门断言这个行为。

## 未验证面（诚实记录）

- **真分配（0/1/0）未在本机验证**：本机只有一块 Apple GPU 且 VideoToolbox 无设备索引。
  代码路径、参数校验、状态上报都已验证，但「NVIDIA 机器上是否真绑到指定卡」需要实机复验。
- VAAPI 未接入（要走 render node 而非序号）。
- 分配只看路数，不看单路开销；若各流分辨率差异很大（1080p 与 320p 混跑），
  按路数分不一定均衡。真要做需要读 NVML 利用率或按像素/码率加权。
