
## 负载自适应降帧（第 6 项，2026-10-29 增）

### 能力

编码跟不上时自动降帧率，CPU 有余量时自动恢复；**降帧靠编码前抽帧实现，关键帧永不丢**。

```ini
[transcode]
adapt_fps=1              ; 默认 0(关闭) —— 不开时行为与以前完全一致
adapt_min_fps=5          ; 降帧下限
```

API：`adapt_fps=1`、`adapt_min_fps=5`。响应回显两项。

### 判据与调参

控制律看 **单帧编码耗时 / 当前帧间隔**（load）：

| load | 动作 | 触发条件 |
|---|---|---|
| > 0.85 | 帧率 ×0.8（下限 `adapt_min_fps`） | 连续 15 帧 |
| < 0.55 | 帧率 ×1.25（上限基准帧率） | 连续 60 帧 |
| 中间 | 不动 | 避免来回抖 |

**为什么不用 CPU 占用率**：多核机器上 30% 占用也可能已经喂不饱这条流；别的进程抢 CPU
又会让我们误判。直接量「这一帧编了多久」才是可归因的指标。

### 三条必须同时成立的验收判据

1. **降得下来**：过载时帧率明显低于目标（实测 30 → 10.8fps），且不低于下限；
2. **不错位**（最容易漏）：降帧后 5 秒拉流里的视频时长仍 ≈5 秒。
   **只降帧不改时间轴步进 = 慢放**（15→7.5fps 会让 5 秒拉流只推进 2.5 秒内容，音画错位）。
   这条只有量 pts 跨度才能发现 —— 看包数、看「能不能播」都发现不了；
3. **不花屏**：关键帧不能被抽掉（丢 I 帧 = 下游没有 GOP 起点 = 花屏/黑块），
   落盘后重新解码必须 0 错误。

### 测试钩子

`ZLM_ADAPT_SELFTEST_DELAY_MS` 环境变量：给**测得**的编码耗时人为加 N 毫秒，
用来在快机器上确定性复现「过载」。用环境变量而不是配置项/API，是为了不把
「会让转码变慢」的开关暴露给运维；生产不设置即 0。

### 验收

`scripts/adapt_fps_test.py`（11 项）：

| 场景 | 期望 | 实测 |
|---|---|---|
| 无过载 | 帧率保持目标 | 29.3/30 |
| 中度过载(60ms) | 降帧、时长仍 5s | 10.8fps、4.99s |
| 重度过载(400ms) | 继续降但不低于下限 | 9.9fps（下限 5） |
| `adapt_fps=0` + 过载 | 不降帧 | 29.3 |
| 全场景 | 有关键帧、重新解码 0 错误 | 4/2 个关键帧、0 错误 |

### 已知边界

- 降帧时编码器的 `gop_size` 是启动时按基准帧率设的，降帧后 GOP 的**时间长度**会变长
  （帧数不变）。影响是观众中途加入等关键帧的时间变长，不影响正确性。
- 只处理视频；音频不做降帧（降音频帧率等于改采样率，会破音）。
