# 昇腾零拷贝（VDEC → VENC 设备直通）可行性验证

> 结论：**可行，且已验证出正确画面**。720p 每帧省 0.85 ms（吞吐 +9.5%），
> 代价是要改转码管线的帧交接方式（当前管线以 host AVFrame 为中转）。
> 生产化预计 3~5 天，风险集中在生命周期与并发回归，不在硬件能力。

## 1. 验证方法

独立探针 `tools/ascend/ascend_zero_copy_probe.cpp`，同一份 H.264 ES、同一个 VENC 参数，
只改「帧怎么交给编码器」：

| 模式 | 路径 |
|---|---|
| `--copy` | VDEC 输出 → `aclrtMemcpy` D2H → host NV12 → `aclrtMemcpy` H2D → VENC（生产现状） |
| `--zero` | VDEC 输出的设备地址 → 直接交给 VENC，不做任何主机往返 |

判据三条：① 两条路都能编出可解码的 H.265；② 画面与源一致；③ 零拷贝明显更快。

## 2. 实测结果（192.168.210.89，2×310P3）

```
零拷贝: 送包=150 解码=144 编码=144 用时=1.22s → 118.4 fps, 每帧 8.45 ms
零拷贝: 送包=150 解码=140 编码=140 用时=1.19s → 118.0 fps, 每帧 8.48 ms
零拷贝: 送包=150 解码=144 编码=144 用时=1.22s → 118.4 fps, 每帧 8.44 ms
零拷贝: 送包=150 解码=148 编码=148 用时=1.25s → 118.8 fps, 每帧 8.41 ms
拷贝  : 送包=150 解码=140 编码=140 用时=1.30s → 107.5 fps, 每帧 9.30 ms
拷贝  : 送包=150 解码=140 编码=140 用时=1.30s → 107.4 fps, 每帧 9.31 ms
拷贝  : 送包=150 解码=146 编码=146 用时=1.36s → 107.7 fps, 每帧 9.28 ms
拷贝  : 送包=150 解码=142 编码=142 用时=1.32s → 107.5 fps, 每帧 9.31 ms
```

- 吞吐 **118.4 fps vs 107.5 fps（+9.5%）**，每帧省 **0.85 ms**
- 两条路输出都是可解码 H.265，帧数一致（144/144、140/140 …）
- 画面校验（720p 测试图，逐帧亮度均值/标准差）：
  `zero` 与 `copy` 从第 2 帧起都与源完全一致 `(126.0, 55.8)`，第 1 帧略偏是预热帧

**带宽账**：720p NV12 一帧 1.38 MB，拷贝路径每帧多搬 D2H+H2D = 2.76 MB。
16 路 × 25fps = 400 帧/秒 ⇒ 少搬 **约 1.1 GB/s** DRAM 流量（1080p 再乘 2.25）。

## 3. 踩到的四个坑（都已在探针里修掉并注释）

1. **VDEC 必须由调用方提供输出缓冲**：`pic.vir_addr=0` 报 `BAD_ADDR(0xA0058011)`；
   `vir_addr` 和 `buffer_size` 都不给报 `BAD_PARAM(0xA0058003)`。
2. **输出缓冲不能只给一块**：VDEC 要留参考帧，单缓冲会被它自己覆写，
   表现为「码流能解、画面和源对不上」。改成 8 块轮转（`frame_buf_cnt` 量级）后画面正确。
3. **VENC create 之后必须 `set_scene_mode` + `get/set_rc_param` 往返**，缺了能建通道，
   但码流出不来或出的是脏数据（表现为一堆 32 字节重复描述符，不是 `00 00 01` 开头的 NAL）。
4. **送帧后要等出包再读**，紧接着读会拿到没写完的包缓冲；
   零拷贝时还必须等编码器消费完才能 `hi_mpi_vdec_release_frame`，否则缓冲被下一帧覆盖。

## 4. 生产化要改什么（3~5 天）

当前转码管线是 `解码 → host AVFrame → 编码`，零拷贝要在这条路上开一条直通：

1. `AscendVenc::encodeDevice(const void *dev_ptr, int stride, uint64_t pts)`
   —— 编码器直接吃设备地址（探针已验证这条路能出正确码流）。
2. `AscendVdec` 增加「设备帧」出参 + 显式 `releaseFrame()`：由编码侧消费完再放行，
   配合缓冲池轮转（探针用 8 块）。
3. 管线加一条快路径：**源是硬件解码 + 目标是硬件编码 + 无滤镜/无缩放/无 OSD** 时，
   解码帧不落 host，直接交给编码器；其余情况一律回落到现有路径。
4. 回归：16 路并发 + 画质比对 + 与现有 15 套回归共存（现有路径不能被改坏）。

**风险**：不在硬件，而在「生命周期」——设备帧比 host 帧多一个「谁在什么时候释放」的约束，
并发下写错就是花屏/崩溃；且快路径与滤镜路径的分流判断必须严谨，否则用户一开 OSD 就崩。

## 5. 与 #8 的关系

#8「全 GPU 硬件编解码与滤镜，防止显存与内存频繁拷贝」分三块：

| 子项 | 状态 |
|---|---|
| 硬件解码 | ✅ 已完成（昇腾 VDEC / NV CUVID / VideoToolbox） |
| 硬件编码 | ✅ 已完成（昇腾 VENC / NVENC / VideoToolbox） |
| **解码帧直通编码（本文件）** | ✅ **可行性已验证**，生产化 3~5 天 |
| GPU 滤镜（缩放/OSD 在 GPU 上） | ❌ 未做：昇腾要走 VPC/DVPP，NVIDIA 要走 CUDA 滤镜链 |

即：本文件关掉的是 #8 里「编解码之间不来回搬」这一半；GPU 滤镜是另一半，还没动。
